# Harness audit, 2026-11-05

Scope: `run_isabelle_solver.py`, `harness/ib.py` (verifier), `harness/arms.py`,
`harness/mcp_bridge.py`, the prompts, and the parts of the Isabelle Pool Server
(IPS) the verifier leans on. Reference design: `~/GitHub/isabelle-humanize`
(the RLCR flow: `flows/isabelle_rlcr/{arbiter,gates,__init__}.py`, its prompts,
STATUS.md and the run archive), which solved IMO 2026 P1 twice with DeepSeek on
the same server family. Evidence from our side: the Q1 plain-arm rerun of
2026-11-05 (`runs-server/Q1_plain_rerun1/`, 280 model calls, stopped by hand).

Findings are ranked. Each names the file, the failure, the evidence and the
fix. The three fixes made earlier the same day (timed-out check as an error, no
build on a stuck file, outage wording, 1800 s build limit) are assumed.

**Status after the owner's review (same day):** F1, F2, F3, F5, F6, F7 applied
(`tests/test_harness.py`, 20 tests; `ib.py selftest`). F4: analysis delivered,
no change (upstream parity kept unless the owner decides otherwise). F8: **no
prompt change** -- the owner wants to measure what mechanical goal binding
would add, so the prompt must not pre-empt it. F9 to F12 open.

## Findings

### F1 (high) The file can change after `completed()` passes, and the verified bytes are not kept

`run_isabelle_solver.py`, `write_file` / `write_disproof` / the loop.
DeepSeek issues several tool calls in one turn (34 of 280 turns in the Q1
transcript). agentlib executes them in order. If a turn carries
`completed()` followed by `write_file`, the PASS is recorded in `at.kind`, the
loop stops after that turn, and the final re-verify runs on the **modified**
file. A proof that passed is then scored `failed`, with no copy of what
passed. Humanize commits the verified bytes and reverts to them when its
finalize pass breaks the build.

Fix: once `at.kind` is set, `write_file` and `write_disproof` return "the run is
over; the file is frozen" without writing. On PASS, copy the text to
`verified.thy` in the bench dir and have the post-loop re-verify prefer it. Two
small edits plus a test.

### F2 (high) Verifier hole: ML inside a proof method

`harness/ib.py` FORBIDDEN screens top-level commands (`ML`, `setup`,
`oracle`, `axiomatization`, ...). The IPS denylist
(`server/app/core/diagnostic_guard.py`) screens the same set. Neither covers
the **proof methods** `tactic` and `raw_tactic`, which take an ML cartouche
inside a `by`/`apply`. ML there reaches `Skip_Proof.make_thm`, the oracle
behind `sorry`, without the `quick_and_dirty` check; `isabelle build` records
the oracle and passes. The prompt forbids ML, the verifier must too.

Fix: add to FORBIDDEN
`(r"\b(raw_)?tactic\s*(\\<open>|‹|\")", "tactic (ML in a proof)")`
and a selftest case. Report the same gap to IPS (`_DANGEROUS_RE`). While there:
`\<proof>` is Isabelle's synonym for `sorry`; the regex misses it, the build
catches it ("Cheating requires quick_and_dirty mode!"). Add it for the textual
check's completeness.

### F3 (high) The post-loop re-verify can sit on a stuck file for 30 minutes

`_solve_one`: after a wall-clock timeout the harness closes the bridge, then
calls `ib.verify_text`, which builds whatever is on disk with the 1800 s
limit. A file with a divergent step (today's metis) costs the full limit and
leaves an orphaned `poly` on the server (IPS kills the wrapper, not the ML
process). With two workers that blocks the other worker's `completed()` builds
for the same time, since the server runs one bigstep at a time.

Fix: run the post-loop verify **before** closing the bridge, call
`at.stuck_line()` first, and skip the build (reason `stuck at line N`) when the
session never finished checking. Only when the bridge is gone (setup error)
fall back to the blind build.

### F4 (medium) `completed()` builds files the session already reports as broken

Upstream nearai runs `lake build` on every `completed()`, so this is parity,
but the Isabelle build is slower (minutes with heaps loading) and the session
has already told the model the exact errors after each write. Humanize's
arbiter only runs when readiness says `success` and the proof is closed, and
never had a wasted arbiter call in its archive.

Option: in `completed()`, after the textual checks, read the session report;
when it has errors or `proof_open`, return FAIL with those lines and no build.
Cost: one `isabelle_sync` plus one diagnostics call, both sub-second on an
unchanged file. Risk: a stale or rebound session; mitigated because the report
is from the current text. Owner's call, since it moves away from upstream.

### F5 (medium) 300 s may still be too short for the IMO theory class, and the tool timeout must track it

Humanize raised its readiness budget to 600 s for P1 after `load_document`
exceeded 180 s on the 1000-line file. Our `LOAD_TIMEOUT_S` is 300. A legitimate
full check of a finished P1 proof is in the 100 to 200 s range here (the two
Q1 loads took the whole 120 s budget, so the true number is unknown).
`TOOL_TIMEOUT_S` is 330 and must stay above the load budget plus the
diagnostics call, otherwise the bridge times out the call and the model sees a
generic "Tool call timed out" instead of the stuck-line report.

Fix: `LOAD_TIMEOUT_S` 600, `TOOL_TIMEOUT_S = max(330, LOAD_TIMEOUT_S + 120)`.
The wall clock absorbs it; a check that needs 10 minutes is itself a signal.

### F6 (medium) The prover side of the conversation is not in the transcript

`transcript.jsonl` records agentlib tool calls (what the model asked and got
back). The MCP calls the harness makes inside those tools, `isabelle_sync`,
`isabelle_diagnostic_messages`, `isabelle_fill_sorries`, their raw JSON, are
not recorded anywhere. Today's diagnosis needed the server log and a replay on
a local server to learn that the report said `timed_out`. Humanize journals
every readiness report per round.

Fix: `_Attempt.mcp` emits `{"kind": "mcp", "name", "args", "result", "elapsed_s"}`
to the same sink (`agentlib.TOOL_SINK` is already the attempt's transcript).
Ten lines; `transcript_view.py` needs one more branch.

### F7 (medium) `disproved()` accepts a disproof that does not build

`disproved()` records the claim when `DISPROOF.thy` exists and is non-empty.
`write_disproof` builds it and reports the outcome, but nothing stores that
outcome, so a failed build followed by `disproved()` ends the run as
`disproved`. The prompt discourages this; the harness should not allow it.

Fix: remember the last `write_disproof` build result on the attempt and have
`disproved()` refuse unless it passed. Human review remains the final check.

### F8 (medium) Sledgehammer under-use in the plain arm, and the goal-binding wording

Q1 plain arm: 9 `isabelle_sledgehammer` calls against 111 `isabelle_run_code`
and 54 `isabelle_multi_attempt`; the model closed most steps by hand and
reached for sledgehammer late. Humanize saw the same (2 calls in 4 h) and
rewrote its rule to "sledgehammer early and often: two edits on the same
subgoal without closing it means sledgehammer now". Their P1 solve used 0
metis/smt and went scratch-first (42 `run_code`).

This is a prompt decision that touches the treatment variable (the plain arm
*is* per-goal sledgehammer), so it is the owner's. Two separate choices:

1. Strengthen `_PLAIN_STRATEGY` step 8 to the early-and-often form. The
   skeleton arm gets sledgehammer automatically, so the asymmetry is the
   experiment, not a confound.
2. Add to the SOLVER RULE text "a suggestion is for the goal it was found
   on; pasting it elsewhere is allowed but it will often loop". The rule stays
   textual (owner decision: no mechanical goal binding), the model is told
   why its file will stall.

### F9 (low) Result taxonomy

`status` is `solved | disproved | timeout | failed`. A verifier outage now
ends as `failed` with `verify: FAIL [..] verifier unavailable`, and a stuck
check as `failed` with the stuck line. `analyze.py` should treat the outage as
missing data, not as a failure of the arm. Add `status: unverified` for it.

### F10 (low) Solver-rule false positives inside literals

`extract_solver_calls` runs on comment-stripped text, not literal-blanked
text. A `text ‹we tried metis here›` block or a string containing `smt` makes
`write_file` reject the file as an unsanctioned call. IPS has
`strip_isar_literals` in `server/app/core/input_guards.py`; port it (20 lines)
and run the solver rule on the command skeleton.

### F11 (low) The prompt does not state the no-internet rule

Mechanically moot: there is no bash and no web tool, the model API has no
browsing, IPS blocks ML. Humanize states it in every prompt anyway and it
is what a reader of the transcript will look for. One sentence in `# Rules`.

### F12 (low) IPS items to hand off

- A timed-out bigstep build kills the `isabelle` wrapper and waits on pipes
  the orphaned `poly` keeps open: the request never answers, the per-theory
  lock stays held, the next build of the same text queues behind it
  (`build_verify.py` `_run_build`). Kill the process group, or close the pipes.
- `_DANGEROUS_RE` lacks `tactic` / `raw_tactic` (F2).
- `isabelle_diagnostic_messages` emits per-command status only for commands
  that carry a message; a `running` command with no message is invisible.
  Adding `timed_out` and `stuck_line` to its result would let clients see it
  without a second call.

## What is sound and should stay

- The textual verifier is stronger than humanize's arbiter on every axis but
  F2: frozen header and statements (multi-target: every definition block and
  theorem), exactly-once statement rule, shadowing check, 12 escape-hatch
  patterns, comment-aware normalization. `ib.py selftest` covers it.
- The readiness signal comes from the file session the model holds, so there
  is no second session to starve, unlike humanize's per-round REST acquire.
- Capacity refusals are absorbed in `_Attempt.mcp` with release-and-retry;
  hidden tool names are rewritten out of results and descriptions. Humanize
  lost 31 steps once to a model diagnosing 503s.
- The transcript captures every model request including the system prompt and
  tool schemas, and every reply with reasoning, as the owner required.
- The arms differ only in tool list, auto-fill and the strategy paragraph.
  `test_arm_tool_sets_are_disjoint_on_the_treatment` pins it.
- Build parent session comes from the frozen imports at prepare time, so it
  cannot drift from the text (humanize had to derive it per build because its
  builder may edit imports).

## Suggested order

F1, F2, F3 are each under 30 lines and close real ways to lose or fake a
result; do them before the next paid run. F5 and F6 are cheap and make the
next failure diagnosable from the transcript alone. F4, F7, F8 are decisions
for the owner. F9 to F11 are polish.
